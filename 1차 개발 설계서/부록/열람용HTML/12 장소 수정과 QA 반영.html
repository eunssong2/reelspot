장소 수정의 서버·데이터 계약 보완 (Q23)

현재 설계 OpenAPI의 visitCreate는 추가, planUpdate는 순서·시간·날짜 제목 수정이다. 이 둘만으로 장소 이름·주소·위치 수정과 장소 교체를 처리했다고 표시하지 않는다. 전용 변경 operation·요청/응답·오류 코드와 저장 방식은 구현 전에 확정해야 하며, 이번 문서는 다음 불변식을 요구한다. UI50의 기존 API 연결은 조회·시간 변경 범위만 가리킨다.

1. 조회 키는 모임·일정·방문이다. 서버는 현재 참여, 취소·만료 여부와 버전을 확인한다. 외부 공급자 장소 ID를 앱 방문 ID와 혼용하지 않는다.

2. 정보 수정은 방문 식별자·날짜·순서·기록 연결을 유지한다. 공유 장소 행을 그대로 수정해 다른 날짜/모임의 정보를 바꾸지 않는다. 공급자 원본과 사용자 수정값을 분리하거나 방문별 사본을 쓰는 저장 방식을 확정한다.

3. 이름은 1~100자, 주소는 선택·기존 200자 한도, 좌표는 둘 다 없거나 유효한 쌍, 방문 시간은 HH:mm 또는 미정이다. 값을 생략하면 유지하고 명시적으로 지운 경우만 삭제한다. 수정하지 않은 좌표를 화면 전환 때문에 지우지 않는다.

4. 교체는 숨김·검토·보존 기록과 진행 중 업로드가 없는 방문만 허용한다. 화면의 가시 기록 수가 0인 것만으로 허용하지 않는다. 교체와 새 업로드 접수가 경합해도 트랜잭션 안에서 검사하며 한쪽만 확정한다. 같은 날짜 중복 장소와 15개 한도를 유지한다.

5. 순서 편집에서 수정 진입 전 저장을 기다린다. 실패·버전 충돌이면 이동하지 않고 사용자 입력을 유지한다. 성공 후 새 버전으로 조회하고 장소 수정 후 원래 화면에 이름·주소·시간·기록 개수를 갱신한다. 31~100자 기존 날짜 제목(Q15)을 자르지 않는다.

6. 중복 탭·응답 유실에는 같은 요청 결과를 확인하며 방문을 추가 생성하지 않는다. 좌표/이름만 변경해도 서버 저장 확인 전 성공 메시지를 띄우지 않는다.

정적 대조에서 발견한 주의점: toItineraryPlace는 검색 결과의 lat/lng를 복사하지 않는다. toggleManual은 핀을 비우고, 초기 editPlace 좌표를 지도 로딩 후 setPin으로 재표시하는 처리는 확인되지 않는다. recordsForVisit의 가시 기록 검사는 서버의 비공개 기록/업로드 잠금을 대체하지 않는다. 이들은 실행 재현 전 코드상 위험이며 그대로 제품 요구로 채택하지 않는다. UI50 검수에는 기존 핀 표시, 검색/직접 전환 후 변경 없는 저장, 기록 연결 유지도 포함한다.

업로드·편집·저장·삭제의 적용 범위

- QA-02: 현재 장소 기록 화면을 유지한다. 이번 submission의 서버 공개 완료 파일만 종류별로 센다. 사진 N장을 업로드했습니다.는 사진 성공 수이며, 영상/혼합 제출은 종류를 구분한다. 접수·전송 100%·검토 대기를 성공으로 세지 않는다. 이전 완료 작업을 이번 안내에 합산하지 않는다. 부분 실패·오프라인·재시도·취소·응답 유실 복구는 유지한다.

- QA-03: Android 시스템 선택기의 선택 묶음 미리보기와 앱의 사진별 확대/자르기를 구분한다. 시스템 선택기의 내부 UI를 바꿀 수 없으므로 Q25에서 자체 갤러리(선택 전 편집)와 시스템 선택기 유지 후 후보 목록 편집을 고객에게 확인한다. 자체 갤러리의 전체/부분 사진 접근·권한 거부 대안과 F13의 전체 앨범 권한 비강제 정책 변경을 함께 결정한다. 임시안은 후자이며 승인된 요구가 아니다. 한 장 편집 적용/취소가 다른 선택·순서·기기 원본에 영향을 주면 안 된다. 편집 후 크기·형식·중복을 다시 검사한다. 참조 앱의 필터·문자·스티커·그리기 전부를 확정 범위로 보지 않는다(Q25).

- QA-04: 현재 화면의 저장 동작 하나로 준비·다운로드·기기 쓰기를 진행한다. 별도 페이지와 두 번째 저장 버튼은 제거한다. 실제 갤러리 파일 쓰기 성공 뒤 메시지를 표시한다. 권한 거절·공간 부족·만료·부분 실패는 현재 화면에서 안내하고 실패만 재시도한다. 동영상은 포스터가 아닌 영상 파일로 저장한다.

- QA-05: 버튼 위치·시트 유지 여부는 Q27 고객 확인 대기다. 결정 전 기존 기록 메뉴 진입을 임시 유지한다. 본인 기록의 삭제 → 삭제하시겠습니까? → 예/취소. 타인 기록은 삭제할 수 없고 서버도 검증한다. 기록 메뉴의 수정 기능은 제거하지만 F17의 다른 진입이나 metadataPatch API까지 폐지했다고 해석하지 않는다(Q24). 기기 원본·이미 저장한 앨범 파일은 서버 기록 삭제로 지우지 않는다.

- QA-07: 화면은 기기 카메라 결과의 다시 시도/확인이다. frontend@015cfac의 upload-sheet.tsx 70~109행은 사진·영상을 후보에 담고, upload()의 업로드하기가 서버에 접수한다. 확인 뒤 자동 전송이 없는 것만으로 전송 결함이라 단정하지 않는다. Q28 결정 전 사진·영상 모두 확인→검증→후보 추가→업로드하기를 임시 유지한다. 기존 후보와 순서를 보존하고 새 파일은 남은 칸에 담는다. 후보 누락·정규화/검증 실패·명시적 전송 실패를 재현한 뒤, 즉시 전송 전환 여부·사진/영상 대칭성·기존 후보 전체 또는 새 촬영 파일만 전송할지를 N01과 함께 결정한다.

QA-06 서버 렌더 계약의 조사 기준

backend@59aca32 브이로그 계약 사본은 현재 서버의 contracts/openapi.json에서 해당 경로와 참조 스키마를 추출했다. 원본 커밋·SHA256을 포함하며 실제 서버 실행이나 정책 승인을 뜻하지 않는다. 설계 부록/openapi.json에는 아직 이 경로가 통합되지 않았다. QA-06의 서버 재현은 이 관찰 사본과 아래 구현을 기준으로 하고, 프로토타입의 로컬 어댑터 미연결 설명으로 대체하지 않는다.

operation경로조사 단계
vlogCreatePOST /groups/{groupId}/vlogstitle·timeline 입력, 소스 접근·타임라인 검증, 작업 생성
vlogGetGET /vlogs/{jobId}본인 작업·소스 접근·만료 확인, state·progress·reason 조회
vlogCancelPOST /vlogs/{jobId}/cancellation본인 작업 취소
vlogContentGET /vlogs/{jobId}/content완료 MP4의 실제 재생/저장 확인

정적 구현 근거: server/services/vlogs.ts는 작업 DTO의 reason에 error_code를 연결하고, server/worker/vlogs.ts는 렌더 실패를 해당 오류 코드 또는 RENDER_FAILED로 기록한다. rendering 상태가 15분 이상 갱신되지 않으면 WORKER_INTERRUPTED로 처리한다. 실제 실패 원인이라고 단정하지 말고 job ID·상태·reason·worker 로그·입력 timeline을 함께 수집한다. 재시도·취소·권한 변경·만료와 결과 파일의 관계는 실제 실행 검수가 필요하다.
