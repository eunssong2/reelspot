## 1. 기록 메뉴 시트를 유지할까요? — Q27

**질문 대상:** 고객, UI 담당·PM 동석

**현재 상황:** N03은 기존 기록 메뉴 시트를 우선 제외하자는 의견이다. QA-04/05는 같은 시트에서 휴대폰 저장을 바로 실행하고 `본인 기록 수정·삭제` 버튼을 `삭제`로 바꾸라는 요청이다. 시트를 없앨지 유지할지 아직 합의되지 않았다.

**고객에게 물을 질문**

- A안: 시트를 유지하고 `휴대폰에 저장`·`삭제`로 단순화할까요?
- B안: 시트를 제외하고 확대 화면 등에 두 동작을 배치할까요? 이 경우 어느 위치에 둘까요?
- 타인 기록에서의 저장·신고·차단 진입은 어디에 둘까요? 타인 기록 삭제는 허용하지 않는 기존 기준을 유지합니다.

**결정 전 기준:** 기존 기록 메뉴 진입을 임시 유지한다. 저장은 별도 페이지 없이 실행하고, 본인 삭제는 `삭제하시겠습니까?` → `예`/취소로 처리하는 요구와 버튼 위치를 구분한다. 확대 화면 직접 배치로 확정하지 않는다.

**함께 볼 자료:** [N03 기존 시트](2026-11-01_앱_점검_캡처/미설계_화면/N03_기록_메뉴_시트.jpg), [QA-04/05 같은 시트](../검수/2026-11-10_앱_QA/스크린샷/image(20261110-131826).png). 관련 검수: TC-F18-05·TC-F19-05.

## 2. 카메라의 확인을 누르면 바로 전송해야 하나요? — Q28

**질문 대상:** 고객, 앱 담당·QA 동석

**현재 상황:** QA-07은 카메라 결과의 `확인` 후 업로드되지 않는다는 보고다. 현재 앱 코드는 사진·영상을 후보 시트에 담고 `업로드하기`를 눌러 전송한다. N01도 촬영 결과·전송 흐름을 비교한 뒤 결정하는 상태다. 즉시 전송되지 않는 것만으로 오류 원인을 확정할 수 없다.

**고객에게 물을 질문**

- A안: `확인 → 후보 시트에 담기 → 업로드하기`의 두 단계를 유지할까요?
- B안: `확인`을 누르면 바로 전송하도록 바꿀까요?
- B안이면 사진과 동영상 모두 같은 흐름인가요? 이미 시트에 담긴 사진·영상도 함께 보낼까요, 방금 촬영한 파일만 보낼까요?
- 기존 후보가 있거나 남은 업로드 수가 부족할 때 어떤 안내와 선택을 제공해야 할까요?

**앱·QA 담당에게 물을 질문:** 보고 당시 확인 후 파일이 후보 시트에 나타났는지, 이후 `업로드하기`도 눌렀는지 확인했나요? 후보 담기·영상 정규화·파일 검사·명시적 전송 중 어느 단계에서 실패했나요?

**결정 전 기준:** 사진·영상 모두 후보 담기 후 명시적 업로드를 유지하고 기존 후보·순서를 보존한다. 즉시 전송 여부는 재현 결과와 N01 결정을 확인한 뒤 확정한다.

**함께 볼 자료:** [QA-07 카메라 결과](../검수/2026-11-10_앱_QA/스크린샷/동영상_업로드_확인_화면.png), [N01 촬영 결과](2026-11-01_앱_점검_캡처/미설계_화면/N01_촬영_결과_확인.jpg). 관련 검수: TC-F12-01·TC-F14-07.

## 3. 사진을 고르기 전과 후, 언제 확대·편집하길 원하시나요? — Q25

**질문 대상:** 고객, UI·앱 담당 동석

**현재 상황:** 현재 화면은 Android 시스템 사진 선택기이고 참고 화면은 카카오톡의 자체 갤러리다. 시스템 선택기 내부에 앱이 원하는 사진별 버튼을 추가하는 방식으로 구현할 수 없다. 선택 화면을 새로 만들지, 선택 후 앱 후보 목록에서 편집할지 결정이 필요하다.

**고객에게 물을 질문**

- A안: 자체 갤러리에서 사진을 고르는 중에 한 장씩 확대·자르기를 해야 하나요?
- B안: 시스템 선택기로 사진을 고른 뒤 앱의 후보 목록에서 한 장씩 확대·자르기를 해도 될까요?
- A안이면 사진 접근 권한 안내와 전체/부분 접근 범위, 권한 거부 시 대안을 어떻게 제공할까요? 기존의 ‘전체 앨범 권한을 강제하지 않는다’는 원칙을 유지할까요?
- 편집 범위는 확대·자르기까지인가요? 참고 화면의 필터·문자·스티커·그리기도 필요한가요? 사진만 대상인가요?

**앱 담당에게 물을 질문:** 각 안의 Android 권한·부분 접근 대응, 개발 범위와 일정을 설명해 주세요. 자체 갤러리를 선택했다는 이유만으로 전체 사진 권한을 필수로 확정하지 않습니다.

**결정 전 기준:** 시스템 선택기와 권한 비강제 원칙을 유지한다. 선택 후 후보 목록 편집은 임시 설계이며 고객 승인으로 간주하지 않는다. 편집 취소 시 선택·순서·기기 원본을 보존한다.

**함께 볼 자료:** [현재 선택기](../검수/2026-11-10_앱_QA/스크린샷/image(20261110-131255).png), [개별 확대 참고](../검수/2026-11-10_앱_QA/스크린샷/image(20261110-131400).png), [편집 참고](../검수/2026-11-10_앱_QA/스크린샷/image(20261110-131514).png). 관련 검수: TC-F13-05.

## 5. 기록 메뉴에서 뺀 정보 수정은 다른 곳에서 유지할까요? — Q24

**질문 대상:** 고객·PM, 앱 담당 동석

**고객에게 물을 질문:** QA-05는 해당 기록 메뉴에서 수정을 빼라는 뜻인가요, 기록 정보 수정 기능 전체가 불필요하다는 뜻인가요? 설명 입력·기존 기록의 일괄 정보 수정이 필요하다면 어느 화면에서 사용할까요?

**결정 전 기준:** 기록 메뉴의 수정 버튼은 제거한다. 다른 진입은 확인 대기로 두고 기존 설명 데이터와 정보 수정 API를 삭제하지 않는다. Q27에서 시트 유지가 선택되더라도 수정 버튼을 자동 복원하지 않는다.

관련 기능·화면: F17·UI20·UI22, TC-F17 전체. 메뉴 위치(Q27)와 기능 유지 범위(Q24)를 각각 결정한다.

## 6. 장소 수정의 버튼 문구를 어떻게 통일할까요? — Q29

**질문 대상:** UI 담당·PM

| 실제 프로토타입 위치 | 현재 문구와 동작 | 확인할 것 |
| --- | --- | --- |
| 장소 수정 입력 폼의 상단 헤더 | `검색` → 검색 모드 | 이 문구와 위치를 최종안으로 쓸지 |
| 수정 중 검색 모드의 상단 헤더 | `다른 장소로` → 입력 폼 복귀 | 복귀 동작을 표현하는 문구로 바꿀지 |
| 수정 모드 검색 결과 목록 | `+ 스팟에 추가` → 장소 교체 처리 | 추가로 오해되지 않도록 어떤 문구를 쓸지 |
| 검색 결과 상세 패널 | `이 장소로 바꾸기` | 목록과 같은 문구로 통일할지 |

기록이 있는 방문에서는 검색 전환 버튼을 숨기는 기준을 유지한다. 담당자가 모드별 최종 라벨·버튼 위치를 표 또는 화면으로 확정하고 프로토타입 반영 담당·일정을 정한다. 현재 도식은 관찰값이며 라벨 수정안이 승인된 것은 아니다. 관련 검수: TC-F10-07.

## 7. 장소 수정은 어떤 서버 계약으로 저장할까요? — Q23

**질문 대상:** 앱·백엔드 담당·PM

현재 설계의 `visitCreate`는 추가, `planUpdate`는 순서·시간·날짜 제목 변경이다. 장소 이름·주소·좌표 수정과 다른 장소로 교체하는 전용 계약이 필요하다.

- 앱과 서버가 사용할 변경 API, 요청·응답·오류, 버전 충돌 처리를 누가 언제 확정할까요?
- 공급자 장소 정보와 사용자 수정값을 어떻게 분리하고, 다른 방문의 정보에 영향을 주지 않게 저장할까요?
- 기록·숨김/보존 기록·진행 업로드가 있는 방문의 교체를 서버에서 어떻게 막을까요? 교체 중 새 업로드가 시작되는 경우도 포함합니다.
- 순서 편집 저장 후 장소 수정 진입, 저장 후 복귀·재조회는 어느 담당자가 연결할까요?
- 검색 결과 좌표 미복사·모드 전환 시 핀 소거·기존 핀 재표시 누락의 코드상 위험을 누가 실행 재현하고 수정할까요?

**회의 산출물:** API/데이터 처리안, 앱·서버 담당자, 계약 공유일·연결일·재검수일. 기존 방문 ID·기록 연결·순서·시간 보존과 실패 시 입력 보존을 완료 조건에 포함한다. 관련 검수: TC-F10-07~09.

상세 불변식: [12번 설계의 장소 수정 서버·데이터 계약 보완](../1차%20개발%20설계서/12%20장소%20수정과%20QA%20반영.md).
