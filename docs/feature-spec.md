# 장소 계획·미디어 조회 기능 명세서

담당: 염혜원 | 버전: v2.3 | 수정일: 2026-10-14 | 상태: 구현·팀 연동용 확정 명세
기준: 기능명세 v1.7, 기능명세서 v1.4 PPT, 확정 사항(1.2). 촬영·업로드·편집 내부, 로그인, 여행방 생성은 다른 담당이며 이 문서에서는 연결 계약만 정의한다.

---

## 1. 제품 정의

### 1.1 한 줄 정의
하나의 여행방에서 날짜별 방문 장소와 순서를 확인·추가·편집하고, 각 방문 장소에 모인 참여자들의 사진·영상을 본다.

### 1.2 확정 사항
| # | 내용 |
|---|---|
| 1 | **방 하나 = 여행 하나.** 구조는 여행방 → 날짜 → 방문 장소 → 기록(게시물) → 파일(사진/영상). 여행방 안에 다른 여행이나 모임을 두지 않는다 |
| 2 | 같은 장소라도 날짜가 다르면 **별도의 방문**이며 기록도 분리한다 |
| 3 | 사진·영상 조회는 항상 `roomId + dayId + visitId`로 한다. 장소명이나 지도 장소 id만으로 조회하지 않는다 |
| 4 | 날짜는 `YYYY-MM-DD` 문자열, 시간은 `HH:mm`(24시간)으로 보관한다 |
| 5 | 방문 식별자 `visitId`는 uuid다 |
| 6 | 장소 추가 후 날짜별 장소 화면(S02)으로 자동 복귀한다. 새 장소는 해당 날짜의 마지막 순서, 방문 시간은 "시간 미정"이다 |
| 7 | 기록 목록 기본은 **업로드 완료 시각 최신순**. 사진 수와 영상 수는 합치지 않고 따로 센다 |
| 8 | 날짜 메모 기능은 만들지 않는다 |
| 9 | 장소 삭제 기능은 별도 합의 전 만들지 않는다 |
| 10 | 권한 기본값: 여행방 참여자는 누구나 장소 추가, 순서·시간·날짜 제목 수정, 대표 사진 변경이 가능하다. 비참여자는 어떤 데이터도 조회할 수 없다 |

### 1.3 담당 범위
| 포함 | 제외(다른 담당, 연결 계약만 7장) |
|---|---|
| 여행방 요약, 날짜별 장소, 장소 검색·추가, 순서·시간·제목 편집, 장소별 기록 조회, 사진 확대·영상 재생, 대표 사진 변경, 업로드 열기·복귀 처리 | 로그인·인증, 여행방 생성·참여자 관리, 촬영·선택·업로드 처리, 영상 병합, 채팅 |

### 1.4 용어
| 용어 | 정의 | 예시 |
|---|---|---|
| 여행방 | 한 번의 여행을 함께하는 참여자의 공유 공간. 이름·기간·참여자를 가진다 | 우리의 서울 여행 / 2026.10.17~10.19 / 5명 |
| 일자 | 여행 기간에 속하는 하루. DAY 번호와 날짜를 함께 표시 | DAY 1 / 10월 17일 토요일 |
| 장소 | 지도 제공자가 돌려주는 실제 장소. 이름·주소·좌표·분류 | 오후의 커피 |
| 방문 장소 | 특정 여행방의 특정 날짜에 담은 장소 항목. 순서·방문 시간을 가진다 | DAY 1의 오후의 커피 |
| 기록 | 한 참여자가 한 번 올린 게시물. 파일 1개 이상 | 수아가 14:12에 올린 사진 3장 |
| 파일 | 사진 또는 영상 1개. 목록의 카드 1장 | |

## 3. 화면 흐름

```
[여행방 선택: 다른 담당] → S01 여행방 요약
S01 ─ 날짜 카드 ──────────────→ S02 날짜별 장소
S01 ─ 배경 이미지 ────────────→ M1 대표 사진 시트
S01 ─ 장소 없는 날짜 "+ 장소 담기" → S03 (해당 날짜)
S02 ─ "+ 장소 추가" ──────────→ S03 ─ 추가 성공 ─→ S02 (자동 복귀)
S02 ─ "편집" ─────────────────→ S05 ─ 저장 ─→ S02
S02 ─ 시간 ✎ ─────────────────→ M2 방문 시간
S02 ─ 장소 카드 ──────────────→ S04 ─ 파일 탭 ─→ V1 (확대·재생)
S04 ─ "+ 사진·동영상 올리기" ──→ [업로드 담당 화면] ─ 복귀 ─→ S04
```
- 뒤로가기는 한 단계 위 화면으로 간다. 모달(M, V1)이 열려 있으면 모달을 먼저 닫는다.
- 사진 보기·장소 추가·순서 편집에서 돌아오면 기존에 보던 날짜를 유지한다.
- 여행방 목록으로 돌아가는 경로는 상위 담당이 제공한다.

| 화면 | 역할 |
|---|---|
| S01 여행방 요약 | 여행방 정보와 날짜별 계획 요약 |
| S02 날짜별 장소 | 선택 날짜의 장소·시간·순서 조회 |
| S03 장소 검색·추가 | 지도·목록으로 검색하고 날짜에 추가 |
| S04 장소별 기록 | 방문 장소에 올라온 사진·영상 조회 |
| S05 순서·시간·제목 편집 | 선택 날짜의 방문 순서·시간·제목 변경 |
| V1 뷰어 | 사진 확대, 영상 재생 |
| M1 대표 사진 / M2 방문 시간 / M3 확인창 | 모달·시트 |

## 4. 화면 상세

공통: 좌우 여백 20, 카드 곡률 20, 주 색상 코랄, 터치 영역 최소 44(주요 버튼 56). 모든 아이콘 버튼에 읽을 수 있는 이름(접근성 라벨)을 붙인다. 긴 장소명·주소·큰 글씨에서도 버튼과 내용이 겹치지 않아야 한다.

### 4.1 S01 여행방 요약
**구성**: 뒤로가기, `AT THAT PLACE`, 참여자 프로필 묶음(최대 3명 + `+N`) / 대표 배너(16:9) / 여행명 / `📅 기간 · N명` / 섹션 제목 / 날짜 카드 목록.
- 섹션 제목: 날짜 1개면 `하루의 스팟`, 여러 날이면 `N일간의 스팟`. 기간의 시작일·종료일을 모두 포함해 카드를 만든다.
- **날짜 카드**: (여러 날일 때만) `DAY n` 배지 + `M월 D일`, 썸네일(첫 장소, 없으면 기본 아이콘), 날짜 제목(없으면 `M월 D일의 장소`), 집계, 이동 표시.
  - 집계 기본 문구: `장소 3곳 · 사진 7장 · 영상 2개`. 사진 0이거나 영상 0인 항목은 생략하고, 둘 다 0이면 `장소 3곳 · 미디어 없음`. 사진에 영상을 합쳐 `사진 N장`으로 표시하지 않는다.
  - 장소가 없으면 `아직 정한 장소가 없어요`와 `＋ 장소 담기`(→ 해당 날짜 S03).
- 카드 선택 → 해당 날짜의 S02.
- 대표 이미지·프로필이 없으면 대체 이미지를 쓴다.
- **집계 조회 실패는 0으로 표시하지 않는다.** 카드에 `집계를 불러오지 못했어요 · 다시 시도`를 표시한다.
- 화면 진입·복귀 시 최신 정보를 다시 조회한다.

### 4.2 S02 날짜별 장소
**구성**: 뒤로가기, 여행명·기간, 참여자 프로필·인원 / DAY 탭 / 본문.
- **DAY 탭**: 날짜가 2개 이상일 때만 `DAY n` + `M월 D일 요일`, 선택 상태 표시. 1일이면 탭을 그리지 않는다.
- 본문: `YYYY년 M월 D일 요일`, (있으면) 날짜 제목, 섹션 `오늘의 장소`, 우측 `☰ 편집`(장소 1개 이상일 때 표시), 장소 카드, 하단 `＋ 장소 추가`.
- **장소 카드**(저장된 순서): 순번, 방문 시간(`HH:mm` 또는 `시간 미정`, 옆에 `✎`), 썸네일(장소 이미지, 없으면 분류 이모지+색 타일), 분류 칩, 장소명, 주소(1줄), 기록 링크.
  - 기록 링크: 파일이 있으면 `사진 a·동영상 b 보기 ›`, 없으면 `아직 기록 없음 ›`. 카드 선택 또는 링크 → 해당 방문의 S04.
  - 시간이 비어 있어도 노출하며 **시간순으로 재정렬하지 않는다.**
  - 방금 추가한 장소는 테두리와 `추가됨` 배지로 강조한다(다음 진입 시 해제).
- 장소 0개: 빈 카드 `가고 싶은 곳을 담아 하루를 채워보세요.`와 추가 버튼.
- 시간 `✎` → M2. 저장하면 즉시 해당 방문 시간만 서버에 저장한다.

### 4.3 S03 장소 검색·추가
**구성**: 뒤로가기, `장소 추가`, `{여행명} · {추가 대상 날짜}` / 검색창 / 분류 칩 / 지도 / 결과 시트.
- 검색창 안내 문구 `장소를 검색하세요 (예: 성수 카페)`. 검색 버튼 또는 키보드 검색으로 요청한다. **빈 검색어는 요청하지 않는다.**
- 분류 칩: `전체 관광지 맛집 카페 숙소`. 검색어를 입력해 검색하면 `전체`, **분류 칩을 선택하면 검색어를 비우고** 그 분류로 검색한다(혼합 조건 혼동 방지).
- 지도: 결과 마커와 이름표, 확대·축소, 지도를 이동한 뒤 `⟳ 이 지역 다시 검색`(현재 지도 영역으로 조회). 거리 기준점은 **검색을 요청한 시점의 지도 중심**이다.
- 현재 위치 버튼은 위치 기능을 제공할 때만 둔다. 권한은 그 버튼을 눌렀을 때만 요청하고, **거절해도 지도 이동·검색어 검색은 가능**해야 한다.
- **결과 시트**: `{N}곳`(현재 불러온 건수이며 전체 장소 수가 아님), 정렬 `관련도순 / 거리순`, 항목(장소명·분류·주소·`검색 위치 기준 거리`·대체 이미지·`＋ 스팟에 추가`). 이미 이 날짜에 담긴 장소는 `✓ 스팟에 추가됨`(비활성).
- **선택**: 마커와 목록 항목을 선택하면 같은 장소를 강조하고 상세 패널(이름·분류·주소·`선택한 날짜`·`이 날의 장소로 추가`)을 연다. **선택만으로 저장하지 않는다.**
- **추가**: `추가`를 누르면 요청 중 버튼을 잠그고(연속 입력 방지) 저장 응답을 받은 뒤 성공으로 처리한다. 성공하면 **S02로 자동 복귀**하며 새 장소를 `추가됨`으로 강조한다. 다른 날짜의 목록은 바뀌지 않는다.
- 중복: 같은 방·같은 날짜·같은 장소는 추가되지 않고 안내 `이미 {날짜} 장소에 담겨 있어요`를 보여 준다.
- 상태 문구: 시작 `장소를 검색하거나 카테고리를 눌러 보세요`, 검색 중 `검색 중…`, 결과 없음 `검색 결과가 없어요. 검색어나 지역을 바꿔보세요.`
- 검색·지도 오류: 오류 안내와 `다시 시도`. 검색어·분류·선택 상태를 보존한다. 지도만 실패하면 이미 받은 목록은 유지한다.
- **응답 경합 방지**: 요청마다 증가하는 요청 번호를 두고, 최신 요청의 응답만 화면에 반영한다.

### 4.4 S04 장소별 사진·영상 기록
**구성**: 뒤로가기, 장소명, `{여행명} · MM.DD 요일` / `＋ 사진·동영상 올리기` / 섹션 제목 / 정렬 / 카드 목록.
- 섹션 제목: 영상이 있으면 `함께 남긴 순간`, 없으면 `함께 남긴 사진`, 옆에 `사진 a·동영상 b`.
- 정렬 토글: `최신순`(기본) ↔ `오래된순`. **실제 지원하는 옵션만 노출한다.**
- **카드 = 파일 하나.** 한 번에 여러 파일을 올려도 파일별 카드로 펼친다. `+N` 배지·콜라주로 합치지 않는다. 각 카드는 원래 게시물·작성자와의 연결을 유지한다.
  - 이미지: 가로폭에 맞춘 4:3 고정 높이, 잘리는 부분 없이 cover. 목록에는 썸네일, 상세 진입 시 원본을 불러온다.
  - 영상: 재생 아이콘과 길이(`m:ss`) 표시.
  - 하단: 작성자 프로필·이름, 업로드 시각, 설명(**없으면 설명 줄을 숨김**).
- 업로드 시각 표시: 24시간 이내 `N분 전/N시간 전`, 그 외 `MM.DD HH:mm`, 값이 없으면 `시간 미상`.
- 정렬 기준: 게시물 단위 업로드 완료 시각(`posted_at`). 없으면 서버 생성 시각(`created_at`)을 쓰고, 같은 시각이면 원래 순서를 유지한다. 같은 게시물의 파일 순서는 `item_order`를 유지한다. 촬영 시각·방문 예정 시각과 섞어 쓰지 않는다.
- 파일 선택: 사진 → V1 확대, 영상 → V1 재생.
- 파일 로딩 실패: 그 카드만 `이미지를 불러오지 못했어요 · 다시 시도`, 다른 카드는 계속 볼 수 있다.
- 기록 조회 실패: `기록을 불러오지 못했어요 · 다시 시도`(빈 목록 문구와 구분). 기록이 정말 없으면 `아직 이곳에 남긴 사진·동영상이 없어요.`
- `＋ 사진·동영상 올리기` → 업로드 담당 화면(7.3). 취소하면 날짜·목록 위치를 유지한다.

### 4.5 S05 방문 순서·시간·제목 편집
- 열 때 현재 날짜의 장소 목록을 **편집용 사본**으로 복사한다. 부제 `DAY n · M월 D일 요일`(하루 여행이면 날짜만).
- **날짜 제목**: 한 줄 입력, 최대 30자, 안내 `n/30 · 비워 두면 "M월 D일의 장소"로 보여요`. 앞뒤 공백은 제거하고 빈 문자열이면 제목을 삭제한다.
- **장소 행**: 순번, 썸네일, 이름, 주소, `방문 시간 HH:mm ✎ / 시간 미정 ✎`(→ M2), ▲▼ 이동 버튼. 드래그는 필수 요구가 아니다.
- ▲▼: 맨 위 행의 ▲, 맨 아래 행의 ▼는 비활성. **장소가 2개 이상일 때만** 이동할 수 있다. 이동 즉시 번호를 미리 보여 준다.
- **저장**: `변경 저장` → 현재 날짜의 **전체 방문 순서·시간, 제목을 한 번에** 저장 → 성공 시 S02 복귀. 저장 중에는 버튼과 입력을 잠가 연속 입력을 막는다.
- **실패**: 화면과 편집값을 그대로 유지하고 `저장하지 못했어요 · 다시 시도`.
- **충돌**: 다른 참여자가 먼저 바꿨으면(버전 불일치) `다른 참여자가 먼저 수정했어요`와 함께 최신 목록을 다시 불러오겠느냐고 묻는다. 편집값을 말없이 덮어쓰지 않는다.
- **이탈**: 변경이 있는 상태에서 뒤로가면 확인창(M3) `계속 편집 / 변경 버리기`. 변경이 없으면 바로 뒤로 간다.
- 순서 변경은 장소·시간·미디어를 삭제하거나 다른 날짜로 옮기지 않는다.

### 4.6 V1 사진·영상 뷰어
- 전체 화면(어두운 배경), 닫기 ✕, 하단에 `작성자 · 작성 시각`과 설명.
- **사진**: 화면에 맞춰 contain. 확대 1~4배, 두 번 탭으로 1배↔2배, 핀치 확대·이동, 하단 `－ n배 ＋` 버튼. 확대할 때 보던 위치를 유지한다.
- **영상**: 열자마자 재생, 기본 컨트롤(재생/일시정지/탐색), 반복 없음. 재생 오류는 `동영상을 재생하지 못했어요 · 다시 시도`.
- 닫기(✕ 또는 시스템 뒤로가기): **영상 재생을 멈추고** 직전 목록 위치로 돌아온다.

### 4.7 모달·시트
**M1 대표 사진**: `앨범에서 사진 고르기`, (직접 올린 사진이 있을 때만) `기본 이미지로 되돌리기`, `취소`.
- 이미지는 시스템 자르기 화면 없이 선택한 사진을 그대로 올리고, 배너가 가운데를 16:9로 채워 보여 준다.
- 업로드 전 긴 변 1600px 이하로 줄인다. 파일 크기 한도는 5MB. 초과·권한 거부·불러오기 실패는 안내창으로 알린다. 취소하면 아무것도 바뀌지 않는다.
- 저장되면 `rooms.cover_url`을 바꾼다. 실패하면 이전 사진을 유지한다.

**M2 방문 시간**: 장소명 표시, 시 ±1(0↔23 순환), 분 ±5(0↔55 순환), 중앙 `HH : mm`, 빠른 선택 `09:00 12:00 15:00 18:00`, `시간 미정으로 두기`, `취소`, `저장`. 초기값은 현재 시간, 없으면 `12:00`. S02에서 저장하면 즉시 서버 저장, S05에서는 편집 사본만 바꾸고 `변경 저장` 때 반영한다.

**M3 확인창**: 제목·본문·`확인`(+선택 `취소`). 되돌릴 수 없는 동작의 확인 버튼은 빨간색.

## 5. 핵심 처리 규칙

| 항목 | 규칙 |
|---|---|
| 날짜 소속 | 추가·조회·순서 변경은 선택한 여행방의 선택 날짜에만 적용. DAY 번호는 시작일 기준 1부터. 기간 밖 날짜는 사용할 수 없다 |
| 방문 식별 | 지도 장소 id와 방문 id를 분리. 같은 장소라도 다른 날짜·여행방이면 새 방문 id |
| 중복 추가 | 같은 방·같은 날짜·같은 (지도 제공자, 장소 id)는 1회만. 클라이언트 버튼 잠금과 저장 계층의 중복 검증을 함께 적용 |
| 추가 위치 | 선택 날짜의 마지막 순서. 저장 응답을 받은 뒤 성공으로 표시 |
| 순서 저장 | 요청의 방문 id가 모두 해당 날짜 소속이고 **중복·누락이 없을 때만** 한 번에 저장. 하나라도 어긋나면 전체 거부 |
| 동시 수정 | 날짜 단위 `version`으로 낙관적 잠금. 저장 요청에 읽은 `version`을 보내고 서버 값과 다르면 충돌 응답 |
| 검색 응답 | 이전 응답이 늦게 도착해도 최신 결과를 덮지 않는다. 결과 수는 불러온 건수 |
| 최신순 | 업로드 완료 시각 내림차순. 누락 시 서버 생성 시각, 둘 다 없으면 `시간 미상` |
| 집계 | 해당 날짜 방문에 연결된 **저장 완료(`saved`)** 파일만 집계. 대기·실패 제외. 사진·영상 분리 |
| 새로고침 | 추가·순서 저장·업로드 완료 후 관련 목록과 요약 갱신. 복귀·재진입 시 재조회. 실시간 공동 편집은 필수가 아님 |
| 날짜 제목 | 0~30자, trim 후 저장, 빈 값이면 NULL(기본 문구 표시) |
| 방문 시간 | `HH:mm`, 입력 UI는 5분 단위, NULL이면 `시간 미정` |

## 6. 데이터 모델과 DB

### 6.1 모델
| 데이터 | 주요 값 | 비고 |
|---|---|---|
| Room | roomId, name, startDate, endDate, coverUrl?, members | 로그인·방 담당 제공 |
| Day | dayId, roomId, date, dayNumber, title?, version | |
| Place | provider, providerPlaceId, name, address, category, latitude, longitude, imageUrl? | 지도 제공자 원본 정보 |
| Visit | visitId, roomId, dayId, place, order, visitTime? | |
| Record | recordId, visitId, author, postedAt?, createdAt, items[] | 업로드 담당이 저장한 게시물 |
| MediaItem | mediaId, recordId, kind, status, thumbnailUrl, mediaUrl, durationMs?, caption?, itemOrder | 사진/영상 1개 = 카드 1장 |

분류(`category_label`)는 `관광지 / 맛집 / 카페 / 숙소 / 장소` 5종으로 정규화한다. 지도 제공자의 분류 문자열에서 위에서부터 먼저 맞는 규칙으로 정한다: `카페` → 카페, `숙박` → 숙소, `음식점` → 맛집, `관광|명소|문화재|공원` → 관광지, 그 외 장소.

### 6.2 테이블 (SQLite 문법, 서버 DB로 옮길 때도 컬럼 의미 동일)
```sql
PRAGMA foreign_keys = ON;

CREATE TABLE rooms (                       -- 방 하나 = 여행 하나
  id           TEXT PRIMARY KEY,
  name         TEXT NOT NULL,
  start_date   TEXT NOT NULL,              -- 'YYYY-MM-DD' (하루 여행은 start = end)
  end_date     TEXT NOT NULL CHECK (end_date >= start_date),
  cover_url    TEXT,                       -- NULL이면 기본 그림
  member_limit INTEGER NOT NULL DEFAULT 5,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);

CREATE TABLE members (
  id         TEXT PRIMARY KEY,
  room_id    TEXT NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  avatar_url TEXT,
  is_me      INTEGER NOT NULL DEFAULT 0     -- 조회하는 사용자 기준(서버 응답에서 계산해도 됨)
);

CREATE TABLE days (
  id          TEXT PRIMARY KEY,
  room_id     TEXT NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  day_number  INTEGER NOT NULL,
  date        TEXT NOT NULL,
  title       TEXT CHECK (title IS NULL OR length(title) <= 30),
  version     INTEGER NOT NULL DEFAULT 1,    -- 순서·시간·제목 저장 때마다 +1
  UNIQUE (room_id, day_number),
  UNIQUE (room_id, date)
);

CREATE TABLE places (                      -- 지도 제공자 장소 원본(한 번만 저장)
  id                TEXT PRIMARY KEY,
  provider          TEXT NOT NULL,         -- 'kakao' 등
  provider_place_id TEXT NOT NULL,
  name              TEXT NOT NULL,
  address           TEXT NOT NULL,
  category_label    TEXT NOT NULL,
  image_url         TEXT,
  lat REAL, lng REAL,
  UNIQUE (provider, provider_place_id)
);

CREATE TABLE visits (                      -- "이 날짜에 이 장소를 담았다"
  id          TEXT PRIMARY KEY,            -- uuid = visitId
  day_id      TEXT NOT NULL REFERENCES days(id) ON DELETE CASCADE,
  place_id    TEXT NOT NULL REFERENCES places(id),
  sort_order  INTEGER NOT NULL,
  visit_time  TEXT CHECK (visit_time IS NULL OR visit_time GLOB '[0-2][0-9]:[0-5][0-9]'),
  created_at  INTEGER NOT NULL,
  UNIQUE (day_id, place_id)                -- 같은 날짜 중복 추가를 DB가 보장
);
CREATE INDEX idx_visits_day ON visits(day_id, sort_order);

CREATE TABLE records (                     -- 한 참여자의 한 번 올림
  id          TEXT PRIMARY KEY,
  visit_id    TEXT NOT NULL REFERENCES visits(id) ON DELETE CASCADE,
  member_id   TEXT NOT NULL REFERENCES members(id),
  posted_at   INTEGER,                     -- 업로드 완료 시각(epoch ms): 최신순 기준
  created_at  INTEGER NOT NULL             -- 서버 생성 시각: posted_at 없을 때 대체
);
CREATE INDEX idx_records_visit ON records(visit_id, posted_at DESC);

CREATE TABLE record_items (                -- 사진/영상 1개
  id           TEXT PRIMARY KEY,
  record_id    TEXT NOT NULL REFERENCES records(id) ON DELETE CASCADE,
  kind         TEXT NOT NULL CHECK (kind IN ('photo','video')),
  status       TEXT NOT NULL DEFAULT 'saved' CHECK (status IN ('pending','saved','failed')),
  url          TEXT NOT NULL,
  thumb_url    TEXT,
  duration_ms  INTEGER,                    -- 영상만
  caption      TEXT,
  item_order   INTEGER NOT NULL DEFAULT 0
);
```
**순서 저장**은 한 트랜잭션에서 다음을 수행한다: ① `days.version`이 요청의 `version`과 같은지 확인(다르면 충돌) ② 요청의 방문 id 집합이 해당 날짜의 방문 집합과 정확히 같은지 확인 ③ `sort_order`와 `visit_time`을 갱신하고 `days.title`, `days.version + 1` 반영. (`sort_order` 유일 제약은 두지 않고 갱신을 한 문장·트랜잭션으로 처리한다.)

**날짜별 집계**:
```sql
SELECT d.id,
       COUNT(DISTINCT v.id)                                AS places,
       SUM(CASE WHEN ri.kind = 'photo' THEN 1 ELSE 0 END) AS photos,
       SUM(CASE WHEN ri.kind = 'video' THEN 1 ELSE 0 END) AS videos
FROM days d
LEFT JOIN visits v        ON v.day_id = d.id
LEFT JOIN records r       ON r.visit_id = v.id
LEFT JOIN record_items ri ON ri.record_id = r.id AND ri.status = 'saved'
WHERE d.room_id = :roomId
GROUP BY d.id ORDER BY d.day_number;
```
**방문의 기록 조회**: `records`를 `COALESCE(posted_at, created_at) DESC`로 정렬하고, 각 기록의 `record_items`를 `item_order`로 정렬하되 `status='saved'`만 포함한다. 화면은 파일 1개를 카드 1장으로 펼친다.

## 7. 팀 연결 계약

### 7.1 입력·출력 요약
| 연결 | 입력 | 이 화면의 처리 |
|---|---|---|
| 여행방 진입 | roomId, 사용자, 방 요약, 참여·접근 상태 | S01 표시. 없는 방·접근 불가는 빈 여행과 구분 |
| 날짜별 조회 | roomId + dayId → 방문 목록·집계 | S02 표시, S01 집계 갱신 |
| 장소 추가 | roomId + dayId + 지도 장소 → visitId | 성공 응답 후 `추가됨`·집계 반영 |
| 순서·시간·제목 저장 | roomId + dayId + orderedVisits[{visitId, visitTime}] + title? + version | 성공 시 복귀, 실패·충돌 시 편집값 보존 |
| 기록 조회 | roomId + dayId + visitId → 게시물·파일 | 파일별 카드, 상세 보기 |
| 대표 사진 | roomId + 이미지 → coverUrl | S01 배너 반영 |
| 업로드 열기 | roomId + dayId + visitId + 표시용 여행명·날짜·장소명 | 업로드 담당 UI를 연다. **표시용 이름을 식별자로 쓰지 않는다** |
| 업로드 복귀 | status + visitId (+ savedCount) | `completed`/일부 저장만 재조회, 취소 시 유지 |

### 7.2 API 제안 (이름·경로는 팀 합의 시 확정)
| 목적 | 요청 | 응답·오류 |
|---|---|---|
| 방 요약+날짜 집계 | `GET /rooms/{roomId}` | room, days[{dayId, date, dayNumber, title, places, photos, videos}] · `404` 없음, `403` 비참여 |
| 날짜의 방문 목록 | `GET /rooms/{roomId}/days/{dayId}` | day(version 포함), visits[{visitId, place, order, visitTime, photos, videos}] |
| 장소 추가 | `POST /rooms/{roomId}/days/{dayId}/visits` body: place | `201 {visitId}` · `409 duplicate` |
| 날짜 저장 | `PUT /rooms/{roomId}/days/{dayId}` body: orderedVisits, title, version | `200 {version}` · `409 conflict`(최신 목록 포함) · `422 invalid_order` |
| 방문 시간 단건 | `PATCH /rooms/{roomId}/visits/{visitId}` body: visitTime | `200` |
| 기록 조회 | `GET /rooms/{roomId}/days/{dayId}/visits/{visitId}/records?sort=latest\|oldest` | records[{recordId, member, postedAt, createdAt, items[]}] |
| 대표 사진 | `PUT /rooms/{roomId}/cover` | `200 {coverUrl}` · `DELETE`로 기본 복원 |

모든 호출은 호출자가 해당 여행방 참여자인지 서버에서 검증한다. 시간은 epoch ms, 날짜는 `YYYY-MM-DD`.

### 7.3 업로드 연결 계약
```ts
// 열기: S04 → 업로드 담당
type UploadRequest = { roomId: string; dayId: string; visitId: string; roomName: string; dateLabel: string; placeName: string };

// 복귀: 업로드 담당 → S04
type UploadResult =
  | { status: 'completed'; visitId: string; savedCount: number }
  | { status: 'cancelled'; visitId: string }
  | { status: 'failed';    visitId: string; savedCount?: number; message?: string };
```
- `completed`, 또는 `savedCount > 0`인 `failed`: 해당 `visitId`의 기록과 그 날짜 집계를 다시 조회한다. 일부만 저장돼도 저장된 목록을 다시 보여 준다.
- `cancelled`: 날짜·목록 위치를 포함해 아무것도 바꾸지 않는다.
- 업로드가 요청되었다는 사실만으로 기록을 추가하거나 `완료`로 표시하지 않는다. **완료 이벤트는 저장된 파일이 조회 가능한 시점에 전달한다.**
- 업로드 담당 소유: "지금 이 순간 남기기" 시트, 선택 파일의 ✕·＋ 버튼, 최대 선택 수, 촬영 길이·용량·권한, 전송·재시도 정책. 이 문서는 해당 숫자 제한을 정하지 않는다.

### 7.4 팀 합의가 필요한 항목
실제 API 경로·필드 이름 / 충돌 시 서버가 최신 목록을 함께 주는지 / 검색 지역 제한·정렬 지원(지도 공급자 정책) / 미디어 응답 형식(원본·썸네일 URL, 만료) / 업로드 완료 이벤트 전달 방식.

| 중복 추가 | 버튼 `✓ 스팟에 추가됨`, 안내 `이미 {날짜} 장소에 담겨 있어요` |
| 접근 불가·삭제된 대상 | `이 여행방 또는 장소를 확인할 수 없어요.` 안내 후 안전한 상위 화면으로 이동 |

| 대표 사진 오류 | 용량 초과·권한 거부·불러오기 실패를 각각 안내, 이전 사진 유지 |

토스트는 약 2초 표시. 성능: 목록은 썸네일, 상세 진입 시 원본을 로드하고, 날짜·검색 조건·목록 위치를 보존해 불필요한 전체 재로딩을 줄인다.

## 부록 B. 기록 예시 데이터 세부 (9장의 합계를 만드는 게시물)

9장의 합계와 화면 통계가 이 표와 일치해야 한다. 게시물 = 한 참여자의 한 번 올림, 시각은 `posted_at`(표시는 `MM.DD HH:mm`).

| 방문 | 게시물(작성자·시각) | 파일 구성 |
|---|---|---|
| 우리의 서울 여행 DAY1 오후의 커피 | 수아 `10.17 14:12` | 사진 3 (설명 `창가 자리 찾았어요`, `라떼 아트가 예뻐요`, 설명 없음) |
| | 도윤 `10.17 14:25` | 영상 0:06 (`김이 모락모락`) + 사진 1 (`디저트도 하나`) → **합계 사진 4·영상 1, 카드 5개** |
| DAY1 서울숲 산책길 | 지호 `10.17 15:32` | 사진 2 (`단풍이 막 들기 시작했어요`, 설명 없음) |
| | 도윤 `10.17 15:41` | 영상 0:08 (`산책길 한 바퀴`) |
| | 나 `10.17 15:50` | 사진 1 (`나도 한 장`) → **합계 사진 3·영상 1** |
| DAY1 작은책방 하루 | — | 기록 없음 |
| DAY2 골목 분식집 | 하은 `10.18 12:40` | 사진 2 (`떡볶이 성공`, `순대는 필수`) |
| | 수아 `10.18 12:55` | 사진 1 → **합계 사진 3** |
| DAY2 한강 노을 벤치 | — | 기록 없음 |
| 성수 당일치기 아침 빵집 | 수아 `10.24 10:41` | 사진 2 (`갓 구운 크루아상`, 설명 없음) |
| 성수 당일치기 작은 전시관 | — | 기록 없음 |

## 부록 C. 코드 구조·의존성·빌드 (React Native / Expo 기준 권장)

### C.1 스택·의존성

설계 원칙: 화면은 저장 계층 함수(방문 추가, 날짜 저장, 기록 조회, 대표 사진 저장)와 업로드 연결 모듈만 의존한다. 서버·DB 교체는 그 함수 안에서만 한다. 순수 로직(중복 검사, 순서 검증, 집계, 정렬)은 외부 의존 없이 분리해 단위 테스트한다.

### C.4 저장 계층 함수 (화면이 부르는 인터페이스)
```ts
addVisit({ roomId, dayId, place }):  Promise<{ ok: true; visitId } | { ok: false; reason: 'duplicate' | 'network' | 'forbidden' }>
saveDay({ roomId, dayId, orderedVisits, title?, version }): Promise<{ ok: true; version } | { ok: false; reason: 'conflict' | 'network' | 'forbidden' | 'invalid_order' }>
setVisitTime({ roomId, visitId, visitTime }): Promise<{ ok: boolean }>
fetchRoom(roomId), fetchDay({ roomId, dayId }), fetchRecords({ roomId, dayId, visitId, sort })
setRoomCover(roomId, imageOrNull): Promise<{ ok: boolean; coverUrl? }>
```
실패 처리 공통: 화면과 편집값을 유지하고 `다시 시도`를 보여 준다. 실패를 저장 완료로 표시하지 않는다.

### C.5 빌드·실행
```powershell
npx expo start -c                 # 개발 확인
npx tsc --noEmit                  # 타입 검사
# 설치 가능한 테스트 APK(Android): JDK 17 + Android SDK 필요, 첫 빌드 약 8분
```
테스트 APK는 디버그 키로 서명하므로 스토어 배포용이 아니다. 스토어 배포용은 릴리스 키로 서명한 AAB가 별도로 필요하다. 비밀 키·서버 인증정보는 앱 번들에 넣지 않는다(공개해도 되는 클라이언트 키만 환경변수로 주입).
