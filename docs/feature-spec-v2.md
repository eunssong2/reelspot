# 장소 계획·미디어 조회 기능 명세서 v2.0 (빌드 앱 반영판)

담당: 염혜원 | 기준: 기능명세 v1.7(2026-10-13) + 빌드된 `dist/ReelSpot-Demo.apk` 실제 동작 | 작성: 2026-10-13
화면 문구·픽셀 단위 세부는 [demo-app-spec.md](demo-app-spec.md), 이 문서는 **제품 기준 + 구현 상태 + 만들 때 필요한 계약**을 한 곳에 모은 것이다.

## 0. 읽는 법 — 상태 표기

| 표기 | 뜻 |
|---|---|
| ✅ | 빌드된 앱에 구현되어 있고 웹/에뮬레이터 중 한 곳 이상에서 확인함 |
| 🟡 | 앱에 구현되어 있으나 확인 범위가 웹까지뿐이거나, 명세와 동작이 일부 다름 |
| ⬜ | 명세 목표이지만 앱에는 **없음**(구현 필요) |
| 🔗 | 다른 팀원 담당 — 연결 지점만 있음 |

"앱에 있다 = 서비스 요구를 만족한다"가 아니다. 데모 앱은 서버·로그인 없이 기기 내 저장으로 동작하므로 ⬜ 항목은 서비스 연동 때 반드시 채운다.

## 1. v1.7 문서 대비 보완 사항 (가장 먼저 볼 것)

### 1.1 확정 사항 — v1.7·앱·SQL 사이의 불일치를 이렇게 정리했다 (2026-10-14)

아래는 문서끼리 어긋나던 곳을 하나로 정한 결과다. 구현은 이 표를 따른다.

| # | 정리한 내용 | 확정 |
|---|---|---|
| D1 | **방 하나 = 여행 하나.** DB는 `trips`+`itineraries`를 `rooms` 하나로 합친다(5.2). 앱의 `tripId`는 데모 전용 값이고, 서비스에서는 `roomId`(= 데모의 `itineraryId`)만 쓴다. 예시의 서울 여행과 성수 당일치기는 서로 다른 여행방이다 | `rooms` 단일 |
| D2 | **날짜는 `YYYY-MM-DD` 문자열**로 보관한다(앱·SQL과 같음). v1.7 5장의 `YYYYMMDD` 표기는 쓰지 않는다 | `YYYY-MM-DD` |
| D3 | **서비스의 `visitId`는 uuid**(`visits.id`)다. 앱의 `itineraryId/dayId/placeId` 합성 문자열은 데모 전용 임시 키다. 화면은 `visitId`를 뜻을 모르는 문자열로만 다루므로 바꿔도 화면 수정이 없다 | uuid |
| D4 | S02 기록 진입 링크는 **수량을 포함한다**: `사진 a·동영상 b 보기 ›`, 기록이 없으면 `아직 기록 없음 ›`. v1.7의 "사진·영상 보기" 문구는 이 규칙으로 대체한다 | 수량 포함 |
| D5 | S02의 `☰ 편집` 버튼은 장소가 **1개 이상**이면 보이고(날짜 제목·방문 시간을 고쳐야 하므로), S05의 **▲▼ 순서 이동은 장소가 2개 이상일 때만 활성**이다(v1.7 "순서 변경은 2개 이상일 때 활성"과 일치). 앱은 현재 버튼 이름이 `☰ 순서 편집`이고 ▲▼는 1개일 때 비활성이 되는 정도라 문구만 맞추면 된다 | 버튼 1개+, 이동 2개+ |
| D6 | 장소 이미지가 없으면 **이모지+색 타일**을 쓴다. 서비스에서 `places.image_url`이 있으면 그 이미지를 쓴다 | 이모지 타일 |

## 2. 제품 정의·용어

- 한 줄: 하나의 여행방에서 날짜별 방문 장소와 순서를 확인·추가하고, 각 방문 장소에 모인 참여자들의 사진·영상을 본다.
- 구조: **여행방(= 여행) → 날짜 → 방문 장소 → 기록(게시물) → 파일(사진/영상)**.
- 방문 장소 = 특정 여행방의 특정 날짜에 담은 장소 항목. 같은 카페를 다른 날 담으면 **별도 방문, 기록 분리**.
- 조회 범위는 항상 `roomId + dayId + visitId`. 장소 이름/지도 장소 id만으로 기록을 조회하지 않는다.
- 채팅, 로그인, 여행방 생성, 촬영·선택·업로드 처리, 영상 병합은 이 담당이 아니다.

## 4. 화면 명세

### 4.0 이동 흐름
```
[상위: 여행방 선택] → S01 ─ 날짜 카드 → S02 ┬ + 장소 추가 → S03 ─ 추가 성공 → S02(자동 복귀)
                     │                        ├ 순서 편집 → S05 ─ 저장 → S02
                     │                        ├ 시간 ✎ → M1
                     │                        └ 장소 카드 → S04 ┬ 사진/영상 탭 → V1(확대·재생)
                     │                                           └ + 올리기 → 🔗 업로드 → S04 복귀
                     └ 배경 이미지 탭 → M4(배경 사진)
```
데모 빌드는 상위 화면 대신 **S0 일정 선택**(버튼 N개)이 시작 화면이다.

### 4.1 S01 여행방 요약 ✅
- 헤더: ‹, `AT THAT PLACE`, 스팟원 아바타(최대 3 + `+N`).
- 대표 배너 16:9(선택 사진 cover / 없으면 기본 그림), 우하단 `📷 배경 변경` → M4.
- 여행명(24px 굵게), `📅 {기간} · {N}명`, 아바타.
- 섹션 제목: 날짜 1개 `하루의 스팟`, 여러 날 `N일간의 스팟`.
- 날짜 카드(기간의 시작·종료일 포함): `DAY n`(여러 날일 때만)+`M월 D일`, 썸네일, 제목(없으면 `M월 D일의 장소`), 통계.
  - 장소 있음: `장소 N곳 · 미디어 K개 (사진 a·동영상 b)`, 미디어 0이면 `미디어 없음`. 사진·영상은 **합치지 않는다**.
  - 장소 없음: `아직 정한 장소가 없어요` + `＋ 장소 담기` → 해당 날짜의 S03.
- 규칙: 집계는 **조회 가능한 저장 완료 파일만**(업로드 대기·실패 제외). 집계 실패는 0이 아니라 재시도 상태(G2).

### 4.2 S02 날짜별 장소 ✅
- 헤더: ‹, 여행명, 기간, 참여자 아바타·`N명`.
- DAY 탭: 날짜 2개 이상일 때만 `DAY n` + `M월 D일 요일`, 선택 탭 코랄. 1일이면 탭 없음.
- 본문: `YYYY년 M월 D일 요일`, (있으면) 날짜 제목, `오늘의 장소`, `☰ 편집`(D5 참조, 앱은 `☰ 순서 편집`), 장소 카드, 하단 `＋ 장소 추가`.
- 장소 카드: 순번, **시간 칸**(`HH:mm` 또는 `시간 미정` + `✎ 수정` → M1), 썸네일, 카테고리 칩·이름, 주소 1줄, 기록 링크(`사진 a·동영상 b 보기 ›` / `아직 기록 없음 ›`). 방금 추가한 장소는 코랄 테두리 + `추가됨`. 카드 탭 → S04.
- 빈 날짜: `가고 싶은 곳을 담아 하루를 채워보세요.` + 추가 버튼.
- 돌아오면 선택된 날짜 유지.

### 4.3 S03 장소 검색·추가 ✅
- 헤더: `장소 추가`, `{여행명} · {YYYY년 M월 D일 요일}`(추가 대상 날짜).
- 검색창 placeholder `장소를 검색하세요 (예: 성수 카페)`, 키보드/돋보기로 검색, 빈 검색어 무시.
- 칩: `전체 관광지 맛집 카페 숙소`. 카테고리 선택 → 검색어 비움 + 해당 분류 검색. `전체`: 검색어 있으면 재검색, 없으면 결과 비움.
- 지도: 핀·이름표, 확대·축소(데모 지도는 결과에 맞춰 자동), `⟳ 이 지역 다시 검색`(현재 영역 기준, 거리 기준점은 요청 시점 지도 중심).
- 결과 시트: `{N}곳` (현재 불러온 건수이며 전체 장소 수가 아님), 정렬 토글, 항목(이름·분류·주소·거리·`+ 스팟에 추가`), 이미 담은 장소는 `✓ 스팟에 추가됨`(비활성).
- 선택(핀·목록)만으로 저장하지 않는다. `추가`를 눌러야 저장.
- **추가 성공 → 즉시 S02로 복귀**, 새 장소는 **선택 날짜의 마지막 순서**, 시간 `시간 미정`. 다른 날짜는 변하지 않음. 같은 날짜 중복이면 토스트 `{이름}은(는) 이미 {날짜} 장소에 담겨 있어요`.
- 빈 상태: 초기 `예시 장소를 검색하거나 카테고리를 눌러 보세요`, 결과 없음 `검색 결과가 없어요. 검색어나 지역을 바꿔보세요.`(서비스 문구; 데모는 "예시 장소 중에…").
- 데모 전용: 모드 칩 `예시 검색 (오프라인)` / `실제 지도 (인터넷 필요)`, 예시 표시(`예시`, `예시 지도 (실제 아님)`).

### 4.4 S04 장소별 사진·영상 기록 ✅
- 헤더: 장소명, `{여행명} · MM.DD 요일`, ‹.
- `＋ 사진·동영상 올리기`(항상 선택 시트 열기까지) → 🔗.
- 섹션 `함께 남긴 순간`(영상 있을 때) / `함께 남긴 사진`, `사진 a·동영상 b`, 정렬 토글 `최신순 ⌄ ↔ 오래된순 ⌄`.
- **카드 = 파일 하나**: 4:3 이미지(가로폭 − 40, cover), 영상은 `▶ m:ss` 배지, 하단에 작성자 프로필·이름·업로드 시각, 설명(없으면 줄 숨김). `+N` 배지·콜라주 금지. 같은 게시물 파일은 원래 순서 유지.
- 탭: 사진 → V1 확대, 영상 → V1 재생(재생 파일 없으면 토스트 `재생은 아직 지원하지 않아요`). 이미지 실패 → 카드 안 `이미지를 불러오지 못했어요`(다른 카드는 정상).
- 기록 없음: `아직 이곳에 남긴 사진·동영상이 없어요.`
- 정렬 키: 게시물 단위 `posted_at` 내림차순(G11).

### 4.5 S05 방문 순서 편집 🟡
- 헤더 `장소 순서 편집`, 부제 `DAY n · M월 D일 요일`(하루면 날짜만).
- 편집용 사본으로 열기. ▲▼ 이동(맨 위 ▲·맨 아래 ▼ 비활성), 번호 즉시 반영. 드래그 없음.
- 같은 화면에서: **날짜 제목**(30자), **방문 시간**(M1). (메모는 범위에서 제외)
- `변경 저장` → 순서·시간·제목을 한 번에 저장하고 S02로. 저장은 장소·미디어를 삭제하거나 다른 날짜로 옮기지 않는다.
- ⬜ 이탈 확인·실패 시 편집값 유지·저장 중 잠금(G3–G5).

### 4.6 모달·시트
| ID | 이름 | 내용 |
|---|---|---|
| M1 | 방문 시간 | 시 ±1(0↔23 순환), 분 ±5(0↔55 순환), 빠른 선택 `09:00 12:00 15:00 18:00`, `시간 미정으로 두기`, `취소/저장`. 초기값 현재 시간, 없으면 12:00. S02에서는 저장 즉시 반영, S05에서는 `변경 저장` 때 반영 |
| M4 | 배경 사진 | `앨범에서 사진 고르기`(자르기 화면 없음, quality 0.4), `기본 이미지로 되돌리기`(직접 고른 사진 있을 때만), `취소`. 용량 한도 1.4M자 초과 시 오류 안내 |
| M5 | 안내·확인창 | 제목+본문+`확인`(+선택 `취소`). 위험 동작은 빨간 `확인`. 웹에서 `Alert.alert`가 동작하지 않아 별도 구현 |
| V1 | 사진·영상 뷰어 | 전체화면. 사진 1~4배(버튼·두 번 탭, 핀치 없음), 영상은 열자마자 재생·기본 컨트롤, ✕/뒤로가기로 닫으면 **재생 중지** 후 목록 복귀 |

### 5.1 앱 타입(현재 코드, `src/prototype/mock/tripData.ts`)
```ts
interface ItineraryPlace { id; name; address; categoryLabel; emoji; tint; visitTime?: 'HH:mm'; visitId? }
interface ItineraryDay   { id; date: 'YYYY-MM-DD'; dayNumber; title?; places: ItineraryPlace[] }
interface Itinerary      { id; tripId; name; startDate; endDate; days: ItineraryDay[] }
interface PlaceRecordItem{ id; kind: 'photo'|'video'; imageUrl: string|number; videoSource?: number; durationLabel?; caption? }
interface PlaceRecord    { id; memberId; time: string; items: PlaceRecordItem[] }
```
⚠ `PlaceRecord.time`이 **표시용 문자열**이다. 서비스에서는 `postedAt: number(epoch ms)`로 바꾸고 표시 문자열은 화면에서 만든다(G11).

### 5.2 서비스 DB 스키마 v2 (SQLite 기준, D1 반영)
앞서 제안한 스키마에서 **`trips`+`itineraries`를 `rooms`로 합치고**, 업로드 상태·표시용 제약을 추가했다. 서버(PostgreSQL 등)로 옮길 때도 컬럼 의미는 같다.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE rooms (                       -- 방 하나 = 여행 하나
  id           TEXT PRIMARY KEY,
  name         TEXT NOT NULL,
  start_date   TEXT NOT NULL,              -- 'YYYY-MM-DD' (하루 여행은 start = end)
  end_date     TEXT NOT NULL CHECK (end_date >= start_date),
  cover_uri    TEXT,                       -- NULL이면 기본 그림
  member_limit INTEGER NOT NULL DEFAULT 5,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);

CREATE TABLE members (
  id         TEXT PRIMARY KEY,
  room_id    TEXT NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  avatar_uri TEXT,
  is_me      INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE days (
  id          TEXT PRIMARY KEY,
  room_id     TEXT NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  day_number  INTEGER NOT NULL,            -- 시작일 기준 1부터
  date        TEXT NOT NULL,               -- 기간 안의 날짜만 허용(앱에서 검증)
  title       TEXT CHECK (title IS NULL OR length(title) <= 30),
  UNIQUE (room_id, day_number),
  UNIQUE (room_id, date)
);

CREATE TABLE places (                      -- 지도 제공자의 장소 원본(한 번만 저장)
  id                TEXT PRIMARY KEY,
  provider          TEXT NOT NULL,         -- 'kakao' | 'demo'
  provider_place_id TEXT NOT NULL,
  name              TEXT NOT NULL,
  address           TEXT NOT NULL,
  category_label    TEXT NOT NULL,         -- 관광지/맛집/카페/숙소/장소
  emoji TEXT, tint TEXT, image_url TEXT,
  lat REAL, lng REAL,
  is_sample         INTEGER NOT NULL DEFAULT 0,
  UNIQUE (provider, provider_place_id)
);

CREATE TABLE visits (                      -- "이 날짜에 이 장소를 담았다" (visitId)
  id          TEXT PRIMARY KEY,            -- uuid
  day_id      TEXT NOT NULL REFERENCES days(id) ON DELETE CASCADE,
  place_id    TEXT NOT NULL REFERENCES places(id),
  sort_order  INTEGER NOT NULL,
  visit_time  TEXT CHECK (visit_time IS NULL OR visit_time GLOB '[0-2][0-9]:[0-5][0-9]'),
  created_at  INTEGER NOT NULL,
  UNIQUE (day_id, place_id)                -- 같은 날짜 중복 추가를 DB가 보장
);
CREATE INDEX idx_visits_day ON visits(day_id, sort_order);

CREATE TABLE records (                     -- 한 참여자의 한 번 올림(게시물)
  id          TEXT PRIMARY KEY,
  visit_id    TEXT NOT NULL REFERENCES visits(id) ON DELETE CASCADE,
  member_id   TEXT NOT NULL REFERENCES members(id),
  posted_at   INTEGER,                     -- 업로드 완료 시각(epoch ms), 최신순 기준
  created_at  INTEGER NOT NULL             -- 서버 생성 시각, posted_at 없을 때 대체
);
CREATE INDEX idx_records_visit ON records(visit_id, posted_at DESC);

CREATE TABLE record_items (                -- 사진/영상 한 개 = 카드 한 장
  id           TEXT PRIMARY KEY,
  record_id    TEXT NOT NULL REFERENCES records(id) ON DELETE CASCADE,
  kind         TEXT NOT NULL CHECK (kind IN ('photo','video')),
  status       TEXT NOT NULL DEFAULT 'saved' CHECK (status IN ('pending','saved','failed')),
  uri          TEXT NOT NULL,
  thumb_uri    TEXT,
  duration_ms  INTEGER,                    -- video
  caption      TEXT,
  item_order   INTEGER NOT NULL DEFAULT 0
);
```
- **집계 쿼리는 `status='saved'`만** 센다(규칙: 대기·실패 제외).
- 순서 저장은 한 트랜잭션으로 `sort_order`를 갱신한다. 순서 요청의 visit id가 모두 해당 `day_id` 소속이고 **중복·누락이 없는지** 검증하고, 하나라도 틀리면 전체 거부(충돌 안내).
- 날짜 집계 예:
```sql
SELECT d.id, COUNT(DISTINCT v.id) AS places,
       SUM(CASE WHEN ri.kind='photo' THEN 1 ELSE 0 END) AS photos,
       SUM(CASE WHEN ri.kind='video' THEN 1 ELSE 0 END) AS videos
FROM days d
LEFT JOIN visits v        ON v.day_id = d.id
LEFT JOIN records r       ON r.visit_id = v.id
LEFT JOIN record_items ri ON ri.record_id = r.id AND ri.status = 'saved'
WHERE d.room_id = :roomId
GROUP BY d.id ORDER BY d.day_number;
```
- 데모 앱은 DB를 쓰지 않고 AsyncStorage JSON(`reelspot.demo.itineraries.v1`, `reelspot.demo.covers.v1`)에 저장한다. 서비스/오프라인 DB를 `expo-sqlite`로 구현할 때는 `PRAGMA user_version`으로 마이그레이션하고, 화면은 `recordsForVisit`·`usePrototype()`만 의존하게 한다(5.3).

### 5.3 저장 계층 계약 (화면이 의존하는 함수)
현재(데모) 구현은 `PrototypeProvider.tsx` + `src/demo/demoStore.ts`. 서비스로 바꿀 때 시그니처를 다음처럼 **비동기·실패 가능**으로 확장한다.

| 현재 | 서비스 목표 |
|---|---|
| `addPlace(itineraryId, dayId, place): boolean` | `addVisit({roomId, dayId, place}) → Promise<{ok:true, visitId} \| {ok:false, reason:'duplicate'\|'network'\|'forbidden'}>` |
| `updateDay(itineraryId, dayId, {places, memo, title?})`(memo는 데모 잔존) | `saveDay({roomId, dayId, orderedVisitIds, times, title?, version?}) → Promise<{ok:true} \| {ok:false, reason:'conflict'\|'network'\|'forbidden'}>` |

## 7. 팀 연결 계약

### 7.1 입력·출력 요약
| 연결 | 입력 | 이 화면의 처리 |
|---|---|---|
| 여행방 진입 | `roomId`, 사용자, 방 요약, 접근 상태 | S01 표시. 없는 방·접근 불가는 빈 여행과 구분(G8) |
| 날짜별 조회 | `roomId + dayId` → 방문 목록·집계 | S02 표시, S01 집계 갱신 |
| 장소 추가 | `roomId + dayId + 지도 장소` → `visitId` | 성공 응답 후 `추가됨`·집계 반영 |
| 순서 저장 | `roomId + dayId + orderedVisitIds + version?` | 성공 시 복귀, 실패·충돌 시 편집값 보존 |
| 기록 조회 | `roomId + dayId + visitId` → 미디어 목록 | 파일별 카드 |
| 업로드 열기 | `roomId + dayId + visitId` + 표시용 이름 | 업로드 UI 열기. **표시용 이름을 식별자로 쓰지 않음** |
| 업로드 복귀 | `status` + `visitId` | `completed`만 재조회 |

### 7.2 현재 코드의 업로드 연결 지점 (`src/demo/uploadBridge.ts`)
```ts
type UploadRequest = { tripId; itineraryId; dayId; visitId; placeId; placeName };
setUploadHandler((req: UploadRequest) => Promise<{ handled: boolean }>)   // 팀원이 등록
requestUpload(req)                                                          // S04 `업로드하기`가 호출
```
- `handled:true`는 "요청을 넘겼다"일 뿐 **업로드 완료가 아니다**. 등록된 핸들러가 없으면 안내창 `업로드 기능은 팀원 구현 영역입니다`만 띄우고 선택 항목은 그대로 둔다. 기록을 임의로 추가하거나 "완료"로 표시하지 않는다.

### 7.3 목표 계약 (G7)
```ts
type UploadResult =
  | { status: 'completed'; visitId: string; savedCount: number }   // 일부만 저장돼도 savedCount 로 알림
  | { status: 'cancelled'; visitId: string }
  | { status: 'failed';    visitId: string; savedCount?: number; message?: string };
```
- `completed`(또는 `savedCount > 0`인 `failed`): 해당 `visitId`의 기록과 그 날짜 집계를 재조회.
- `cancelled`: 날짜·스크롤 위치 포함 아무것도 바꾸지 않는다.
- 완료 이벤트는 **저장된 파일이 조회 가능한 시점에** 전달한다.
- 촬영·업로드 담당이 소유하는 것: "지금 이 순간 남기기" 시트, 선택 파일 X·+ 버튼, 최대 선택 수, 촬영 길이·용량·권한, 전송·재시도. 이 문서는 숫자 제한을 정하지 않는다. (앱의 "최대 10개"는 기존 팀 코드의 값.)

### 7.4 합의가 필요한 항목
실제 ID·API 이름 / 장소 추가·순서 편집 권한(누가 가능한가) / 검색 지역 제한과 정렬 지원 / 동시 저장 충돌 방식(버전값 vs 마지막 저장 우선) / 미디어 응답 형태·업로드 완료 이벤트 / 대표 사진·시간·제목 편집을 정식 범위에 넣을지(EX01–EX03) / 장소 삭제는 합의 전 추가하지 않음.

## 11. 구현 순서 (이 명세로 처음부터 만들 때)

1. **타입·예시 데이터** — 5.1, 9장 → `tripData.ts`, `demoData.ts`, 번들 자산.

4. **화면 순서** — S01 → S02 → S04 → V1 → S05 → M1 → S03(예시 검색·지도) → M4 → S0/TEST 띠.
